# NUT75 网页驱动无法访问设备

## 已确认的原因

2026-10-07，OMEN 上的 NUT75 已被 `hid-generic` 正常识别，但所有
`/dev/hidraw*` 均为 `root:root`、`0600`，没有授予本地用户读写权限。
这会阻止 Chrome 的 WebHID 打开键盘；网页端是否还有协议或固件问题需连接后验收。

本次有线连接实测设备为 `hfdic NUT75`，USB VID:PID 为 `0c45:880c`。
HID report descriptor 显示：

- 接口 `00`、`01`：标准键盘、鼠标与消费控制输入，不开放。
- 接口 `03`：厂商 usage page `0xff68`，64 字节输入/输出。
- 接口 `04`：厂商 usage page `0xff70`，64 字节输入/输出。

`hidraw` 编号会随插拔变化，不可按 `/dev/hidraw2` 等编号写权限规则。

## 选用方案与边界

复用已安装的 Google Chrome（Firefox 不提供 WebHID），使用厂商提供的
HTTPS 网页驱动，不假定 NUT75 支持 VIA/QMK，也不刷写未知固件。

设备专属配置在 `hosts/omen/nut75.nix`，由主机入口显式导入。
`70-nut75.rules` 按 VID/PID 与接口号匹配，只为两个厂商接口添加 `uaccess`。
文件在 systemd 的 `73-seat-late.rules` 之前执行，logind 为当前本地活动会话
授予 ACL，不增加永久用户组权限，不放开其他键盘或鼠标。

不要使用全局 `hidraw MODE="0666"`、以 root 启动浏览器或禁用浏览器沙箱。
`services.udev.extraRules` 输出的 `99-local.rules` 太晚，不能仅在其中添加
`uaccess` 就期待本次事件自动授予 ACL。

## Fn+P 的 Windows 宏

用户确认 Fn+P 在 Windows 上打开“运行”、输入网址后回车。
这不是系统可单独绑定的 Fn+P 事件，而是一串固件生成的按键。本机 `Super+R`
已经打开 Noctalia 启动器，因此可以保留宏，让网址输入匹配专属应用入口。

主机通过 HM `xdg.desktopEntries.nut75-driver` 声明应用入口：名称是用户提供的
`https://weikav.driveall.cn/`，执行命令固定为 Chrome 打开该网址。
Noctalia 官方 Launcher 文档及当前源码 `src/launcher/app_provider.cpp` 确认：
应用搜索匹配名称、generic name、keywords，名称匹配优先。
这让完整网址直接匹配目标入口，不将任意启动器输入交给 shell 执行。

保留原有 `Super+R`，撤销之前新增的 `Super+Shift+P` 替代快捷键；
不改键盘固件、不安装读取全键盘输入的宏拦截后台。
方案需要宏在启动器获得焦点后完整输入网址。若实测缺字或输入到原窗口，
应另行核查固件输入延迟、启动器焦点和输入法，不能把应用入口构建通过当作时序验收。

## 部署与验收

1. 使用仓库现有的 `nr` 重建命令（含主机快照保护），成功后拔插键盘。
   重建会部署规则并重载 udev；拔插使设备重新经过完整规则链。
   重载规则不代表已连接设备获得 ACL。不能拔插时，用以下命令只重新处理两个厂商接口：

   ```console
   sudo udevadm control --reload-rules
   sudo udevadm trigger --action=add --settle /dev/input/by-id/usb-hfdic_NUT75-if03-hidraw /dev/input/by-id/usb-hfdic_NUT75-if04-hidraw
   ```
2. 先手动按 `Super+R`，输入完整驱动网址，确认搜索结果为该网址、描述为
   “NUT75 网页驱动”，回车后用 Chrome 打开网页。
   若新应用入口尚未被发现，重启 `systemctl --user restart noctalia.service`。
   关闭启动器、切至英文输入状态，再按 Fn+P 验收宏是否自动完成同样流程。
   使用 USB 数据线连接键盘，在网页点击连接，选择 NUT75 并授权。
   若此前连接失败，刷新网页后重新连接。
3. 检查稳定设备链接的 ACL：

   ```console
   getfacl /dev/input/by-id/usb-hfdic_NUT75-if03-hidraw
   getfacl /dev/input/by-id/usb-hfdic_NUT75-if04-hidraw
   ```

   预期两个接口均有当前活动用户的 `rw-` ACL；接口 `00`、`01` 及其他设备
   不应因本规则获得访问权限。`stat` 的组权限位可能显示 ACL mask，不能只看它。
4. 在网页上读取键盘当前配置，再测试一项可恢复的设置，确认保存和重新连接后生效。
   网页的手动授权与实际读写必须人工验收，Nix 构建成功不能替代。

若 ACL 正常但仍不能连接，查看 `chrome://device-log` 中 HID 错误，并核对厂商
网页支持的固件、连接模式和设备过滤条件。无线接收器可能使用不同 VID/PID，
需重新检查，不扩大现有规则兜底。不要把后续协议问题误认为缺少 Linux 内核驱动。

## 本次验证结果

- `nix fmt`：格式通过；遍历器提示仓库原有的
  `assets/scripts/toggle-wlsunset` 已删除，与本修复无关，未改动该删除状态。
- `nix flake check`：通过，实际构建并执行检查。
- `nix build .#nixosConfigurations.omen.config.system.build.toplevel --no-link`：成功。
- `git diff --check`、`git diff --cached --check`：通过。
- `udevadm verify`：生成的规则语法通过。
- `udevadm test --extra-rules-dir=…`：对当前全部八个 HID 节点模拟，只有 NUT75
  接口 `03`、`04` 获得 `uaccess` 标签并排队执行 ACL builtin；其他六个节点未获得。
  模拟不执行该 builtin，不证明实际 ACL 已授予。
- 后续运行时复查（14:41）：规则已出现在 `/etc/udev/rules.d/70-nut75.rules`，
  udevd 已在 14:37 重启，但两接口仍只有 `seat` 标签、无用户 ACL。
  说明规则部署尚未转化为设备节点授权，需要拔插或重新触发事件。
  `udevadm trigger --dry-run` 已确认上述稳定链接恰好选择两个目标节点。
- 新增启动器应用入口及 Fn+P 宏仍需重建后验收；实际 ACL 和网页读写验收尚未完成，
  sudo 需要用户交互输入密码，助手未执行系统切换或权限授予。

## 回退

移除 `hosts/omen/default.nix` 对 `nut75.nix` 的导入并重建，再拔插键盘。
撤销网页驱动权限和专属应用入口，不影响普通打字功能和 `Super+R`。
