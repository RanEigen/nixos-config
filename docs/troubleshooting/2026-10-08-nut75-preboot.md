# WEIKAV NUT75 在 HP OMEN / Limine 预启动阶段无输入：证据化调查

调查日期：2026-10-08，已包含用户确认按键后的复查。本报告区分用户复现事实、本机实测（前期只读、后期授权协议操作）、规范要求、参考实现和未验证假设。

- 本机采集及请求失败记录：[原始证据](2026-10-08-nut75-preboot-evidence.txt)。
- 最小标准 HID 协议测试：[nut75-hid-probe.py](../../assets/scripts/nut75-hid-probe.py)。仅 Python 标准库 + libusb，不依赖 PyUSB。
- 没有修改 NixOS/udev/boot 配置，没有刷固件、发送 vendor 请求或写 EFI 变量。用户授权后做了临时接口 detach/claim、标准 HID 请求及两次仅 NUT75 的 USB device reset；reset 时 Linux 自动发标准 SET_CONFIGURATION(1)。最终两个输入接口均恢复 Report Protocol 和 usbhid 绑定。
- **最终更新：已测出固件标准请求/状态恢复问题，但没有唯一确定 BIOS 无输入的机制。** 用户确认先前窗口确实按键，不能再把零包归因于未按键。Report positive control 也零包，无法比较 Boot 与正常 Report 的格式；GET_REPORT(Input) 反复 STALL，Interface 0 在验证过 Boot 状态后经 USB reset 仍保留 Boot，是另外两条实际固件异常证据。

## 1. 已确认事实

### 1.1 复现事实及平台身份

用户最初报告：内置键盘和普通 USB 键盘可用；NUT75 在 HP BIOS 设置和 Limine 中没有有效键盘输入，在 Linux 正常；禁用 Limine 鼠标支持无效。本次未重启复验这些现象。

**后续重要补充**：用户称另一台机器的 BIOS 可以使用（尚未明确是同一把 NUT75，还是客服的样机），并明确表示在 BIOS 和引导时期按 NUT75 键时鼠标指针会移动。新现象使“预启动把某路按键输入作为鼠标动作处理”的机制成为优先线索，而不是简单的“USB 没有输入”。它与 Interface 0 的 Boot Mouse 声明 / Keyboard Report descriptor 错位高度吻合，但尚未取得 preboot packet，不能宣称已经证明原始键盘 report 被误读或定位到某个 endpoint。用户进一步确认：**不用 Fn，普通字母 A、B 也让指针移动**，因此不能再仅用方向键正常导航解释。用户再次补充，随便按几个键，指针均向下单次跳动（原话“往下单独闪动”）。方向和单次动作与 keycode 被读成 Mouse Y 的推演高度吻合；尚未测定实际位移数值，也未取得 preboot packet 确定报告来源。其他 BIOS 可用也不能直接判断 HP 或 NUT75 单方违规。

### 1.2 关键新发现：两个 Boot 接口的描述与 Report Protocol 功能错位

| Interface | 接口声明 | Report descriptor 实际内容 | Endpoint |
|---|---|---|---|
| 0 | HID / Boot / **Mouse** | **Keyboard** application；8 modifier bits，1 reserved byte，6 keycode array bytes；1-byte LED output（Num/Caps/Scroll + padding）；无 Report ID | IN `81`，8 bytes；bInterval=1 |
| 1 | HID / Boot / **Keyboard** | 首个 TLC 是 Mouse；ID 1 Mouse，ID 2 Keyboard NKRO，ID 3 Consumer，ID 4 System；没有 Output item | IN `82`，16 bytes；bInterval=1 |
| 2 | HID / non-boot | 本次没有读到 report descriptor；只有 OUT endpoint | OUT `05`，8 bytes |
| 3 / 4 | HID / non-boot | vendor usage page，64-byte IN/OUT reports | 64-byte IN/OUT |

`bInterval=1` 在 Full Speed 是 1 ms，在 High Speed 是 125 µs。本次 sysfs `ep_81/interval` 和 `ep_82/interval` 已实测为 `125us`；这是 host polling interval，不证明键盘每 125 µs 真正报告一次。

Interface 0 的 62-byte descriptor 开头为 `05 01 09 06 a1 01`，即 Generic Desktop / Keyboard / Application。**它是经典 6KRO 键盘形状，而不是鼠标 descriptor。**

Interface 1 的 ID 2 为 `120 × 1 bit = 15 bytes`，加 ID 正好 **16 bytes**，不是“接近 16”。Usage 仅 `00..77`，不含 modifier usages `e0..e7`。单看该 report，Shift/Ctrl/Alt 无表达位置；修饰键可能由 Interface 0 提供，必须按键抓包确认。

Linux 日志相应显示 Interface 0 为 `USB HID v1.10 Keyboard`，Interface 1 为 `USB HID v1.00 Mouse`，同时创建 Mouse 和 Keyboard input 节点。这些标签由 Report descriptor 解码产生，不代表 UEFI 对 Boot Protocol 的分类。

**尚不能仅凭错位认定违规**：Report Protocol 和 Boot Protocol 可以不同。若 Interface 1 切到 Boot 后正确发送键盘 report，仍可工作；若固件一直把 6KRO 发往 `81`、把 NKRO 发往 `82`，按 Boot 声明绑定的 UEFI 就可能没有正确键盘数据。后一种是当前最值得验证的具体机制。

Interface 2 日志有 `couldn't find an input interrupt endpoint`，且没有驱动绑定。HID 1.11 §4.4 的标准布局以 Control + Interrupt IN 为基础、OUT 可选；此 OUT-only 接口应让厂商解释，不能认证整个配置完全符合标准。**这个接口的告警不是 Interface 1 失效的证据。**

### 1.3 UEFI Console 路径的只读旁证

18:30 重启之前的 `ConInDev`（attributes `BS+RT`，非 NV）包含：

```text
PciRoot(0)/Pci(0x1f,0)/Acpi(PNP0303,0)
PciRoot(0)/Pci(0x14,0)/USB(parent_port=0,interface=1)
PciRoot(0)/Pci(0x14,0)/USB(parent_port=1,interface=2)
```

第二条匹配当前 NUT75 的 controller/root port/Interface 1；第三条匹配当前 Compx 鼠标 dongle 的 Keyboard Interface 2。UEFI USB Device Path 的 parent port 为零基编号，与 Linux `1-1` 的端口 1 对应。[9]

`ConIn` 包含 wildcard `USBClass(ffff,ffff,ff,ff,ff)`，以及 Bluetooth 类 `USBClass(ffff,ffff,e0,01,01)`，不是简单的“只列出内置键盘”。

EDK II 定义 `ConInDev` 为所有可能的 console input devices，ConPlatform 在成功打开设备 Simple Text Input 后追加路径。[9] 因此上述路径是**较强旁证：固件至少认识了 Interface 1 的输入候选**，明显削弱“HP 绝对只扫描 Interface 0”。

18:30 后的新启动仍有 NUT75 的 Interface 1 路径，但没有 Compx 的路径；说明不能把前一启动的 console 列表当作永远固定。本次固件仍认识 NUT75 的输入候选。

但 HP/Insyde 不是已审计的 EDK II 构建；不能凭变量确认 ReadKeyStroke 成功、实际 ConsoleInHandle 的聚合情况或 SET_PROTOCOL 已发送。没有修改这些变量。

### 1.4 规范：Boot / Report / Composite / Endpoint 必须分开判断（C、D、E、F）

权威资料已下载并读相关章节：HID 1.11、HID Usage Tables 1.5、USB 2.0。[1–3] 本次没有取得独立 HID 1.12 正文，不伪造其条款。

**HID 1.11 §7.2.6**：

> “When initialized, all devices default to report protocol.”
> “… should set the desired protocol whenever initializing a device.”

含义：规范默认是 Report Protocol；切到 Boot 后 Linux 正常，或 Linux 下查询为 Report，都不能证明上电和 Boot 行为正确。§F.3 要求 reset 后回到 Report Protocol；§F.4/F.5 要求使用 Boot 的系统配置设备后发 SET_PROTOCOL。

**HID 1.11 Appendix B / F.3**：Boot Keyboard 输入是 8-byte 格式：modifier、reserved、6 keycodes；输出是 1-byte LED bitmap。Boot 系统不需要解析 report descriptor。Appendix B 明确：

> “The report may not exceed 8 bytes in length.”

因此固定 Boot Keyboard 前面不能插入 Report ID，也不能继续发送 16-byte NKRO bitmap。Report Protocol 里的 ID 2 并不违规；收到 BOOT 后仍发送该格式，才是明确的实现不符合 Boot Keyboard 要求。首字节 `02` 也可能是合法 Left Shift modifier，不能仅凭首字节判断 Report ID。

**HID 1.11 §6.2.2 的 Report ID 说明**显式举例允许同一 endpoint 传 key press 和 pointing data。HUT 1.5 §3.4.2.1 允许 selector 使用 `Array[1]`、`Array[n]` 或 bitmap；§3.4.3.2 举 keyboard + pointing device 有多个 application collections 的例子。[1,2]

因此：

- Composite、interface 0 是 mouse / interface 1 是 keyboard：**标准允许**，不能假定 keyboard 必须是 interface 0。
- Report Protocol 的 NKRO bitmap、Report ID、多 TLC：**通用 HID 表达机制允许**，不是 Boot Protocol 不合规的充分证据。
- 首个 TLC 为 Mouse、多功能复用、6KRO 放在声明 Boot Mouse 的接口：**兼容性风险和设计可疑点**，但必须检查实际 Boot 格式再判错。
- “Interface 1 理论上只能含 Keyboard TLC”：没有这样的普遍硬性要求；专用、清晰的 Boot Keyboard 接口是兼容性设计建议。
- HID 1.11 Appendix C 确有 “Non-modifier keys must be reported in Input (Array, Absolute)” 的传统键盘要求；它和后来 HUT 的通用 bitmap 表达应分别说明。因此本报告只确认 NKRO 可被 HID 描述，**不凭通用机制认证此设备全部键盘条款合规**，也不把这句当作其 BIOS 故障已证实的原因。

**USB 2.0 §5.7.3**：Full Speed interrupt payload 上限 64 bytes，host controller 应支持 `0..64` 最大 payload。**`wMaxPacketSize=16` 合法；最大包容量不等于每次 report 长度。** Boot 时在同一 endpoint 发 8-byte short packet 是合理行为，不必改 endpoint descriptor。

EDK II UsbKbDxe 的实际代码读取 endpoint MaxPacketSize 作传输 buffer 长度，KeyboardHandler 要求至少 8 bytes，再解析前 8 bytes。[4] 这证明存在标准实现支持 `MPS=16 / actual=8`，不能证明 HP 一定支持。

主机可在足够大的接收 buffer 内只解析前 8 bytes；**不能说设备发 16 bytes 时主机请求 8 bytes 就能可靠“裁切”**，可能是 overflow/babble。实际 Boot 发 16-byte NKRO 即使被 EDK II 忽略尾部，前 8 bytes 仍不是 keycode array。

### 1.5 Linux 和 Limine 源码（A、I）

Linux usbhid 参考源码在 descriptor parse 阶段调用 `hid_set_idle(...,0,0)` 并解析 report descriptor。[5] 此次取得的 master 文件没有 SET_PROTOCOL 调用；不能把 Linux 工作正常推导成“Linux 已测试过 SET_PROTOCOL(BOOT/REPORT)”。它也不是本机 7.2.9-zen1 的精确源码，初始化请求仍须 usbmon 实测。

本机 Limine **v12.9.1** 的 `common/lib/getchar.c`：

1. 从 `gST->ConsoleInHandle` 尝试 Simple Text Input Ex；
2. 再尝试 Simple Text Input；
3. fallback 到 `gST->ConIn`；
4. 调用 `ReadKeyStrokeEx` / `ReadKeyStroke` 和 WaitForEvent。

没有直接 USB HID 驱动 fallback。对应版本 CONFIG 的 `mouse: no` 只禁止 boot menu 使用 pointer；不能重新分类 Interface 0/1，也不能修复键盘固件。[6]

Limine issue #645：Lenovo 外接键盘同时在 UEFI 设置和 Limine 不可用，维护者明确说：

> “Limine does not have a USB driver and relies on the firmware to do the keyboard handling.”

这支持边界判断，不是 HP/NUT75 已知 bug。[7] Issue #515 是 ASRock Ultra Fast Boot 阻止 USB 输入，提供关闭 Fast Boot 的对照线索，不证明 HP 有同样设置。[8] BUGS.md 还记录某些固件首次读取时延迟初始化，属于时序线索；当前“BIOS 所有按键无效”不能简单归因于 Limine WaitForEvent。

若某输入设备已暴露独立 Simple Text Input 但没有聚合进 ConsoleIn，定制 EFI app/bootloader 理论上可以枚举并读取它；**现版 Limine 不是这样做的**。若设备 Boot 数据本身错误，则需额外的 UEFI HID 驱动/报告解析器，而不是一项 Limine 配置。不是“任何 bootloader 在理论上都无能为力”，而是没有现成 Limine direct HID 修复路径。

### 1.7 用户授权后的 privileged 硬件测试（18:23–18:25）

完整 libusb 日志与仅 NUT75 的 usbmon 捕获保存在 [nut75-preboot-captures/](nut75-preboot-captures/)。URB 内核地址在持久化 usbmon 中替换为一致标签，没有记录密码。

| 实测 | Interface 1（Boot Keyboard 声明） | Interface 0（Boot Mouse 声明） |
|---|---|---|
| 初始 GET_PROTOCOL | `01` Report | `00` Boot（不是上电默认协议的证据） |
| SET_PROTOCOL(1) + GET | 成功，返回 `01` | 成功，返回 `01` |
| SET_PROTOCOL(0) + GET | 成功，返回 `00` | 成功，返回 `00` |
| SET_IDLE(0)、GET_IDLE | 成功，读回 `00` | 成功，读回 `00` |
| SET_IDLE(125)、GET_IDLE | 成功，读回 `7d`（500 ms） | 成功，读回 `7d` |
| GET_REPORT(Input) Report | ID 2、16 bytes：STALL | ID 0、8 bytes：STALL |
| GET_REPORT(Input) Boot | ID 0、8 bytes：STALL | ID 0、3 bytes：STALL |
| GET_REPORT Boot LED | 1 byte：STALL；因此没有 SET_REPORT LED 写入 | 没有测试 |
| 5 个 interrupt 接收窗口 | 全部零包，包括 Report 基线 | 全部零包，包括 Report 基线 |
| 恢复 Report + release/reattach | 成功，driver=sysfs usbhid | 成功，driver=sysfs usbhid |

usbmon 验证控制请求确实完成：SET/GET_PROTOCOL 和 SET/GET_IDLE completion status `0`；GET_REPORT completion `-32`（STALL / EPIPE）。接收 timeout 后的 interrupt `-2` 是主机取消 URB，不是设备报告了某个键或明确 endpoint STALL。

HID 1.11 §7.2 将 GET_REPORT 标为 mandatory。**对已声明的 Input report 反复 STALL 是实际的固件合规问题证据**；它不等于已经找到了 BIOS 无输入的直接原因，因为 Boot host 可能主要依赖 interrupt IN，不用 GET_REPORT(Input)。

SET_IDLE(500 ms) 后 8 秒内也没有 periodic report，说明“成功存储/读回 idle 值”没有证明真实 idle 行为正常。用户随后确认测试期间确实按了键，因此要调查为什么连 Report positive control 都收不到，而不是反复要求按键或直接判定 Boot 包是 NKRO。

无 detach 的首次 GET_PROTOCOL 返回 IO；kernel 同时记录 `did not claim interface 1 before use`。claim 后立刻成功，所以该首次 IO 不应作为 GET_PROTOCOL 不支持的证据。

当前结论更新：**可以排除‘Interface 1 完全拒绝 SET_PROTOCOL’；不能排除‘只改变 protocol 状态变量，没有改变输入格式/路由’。**

### 1.8 用户确认按键后的复查：排除测试干扰并验证 USB reset

详细记录：

- [完全被动、驱动绑定的 usbmon](nut75-preboot-captures/passive-high-speed-bound.log)：60 秒没有 NUT75 成功 input completion。
- [驱动绑定 + hidraw/event 只读打开](nut75-preboot-captures/bound-hidraw-high-speed.log)：30 秒没有输入；同一 trace 成功捕获标准 GET_DESCRIPTOR(Device)，18 bytes，证明目标/抓包通路可用。无 class request / detach / protocol change。
- [双接口并行、不在输入窗口前发 GET_REPORT](nut75-preboot-captures/paired-high-speed-no-get-report.log)：initial `(0,1)`、两个 Report `(1,1)`、Keyboard Boot/Mouse Report `(1,0)`、两个 Boot `(0,0)`、idle 500 ms 均零包。协议状态独立切换，没发现 GET/SET_PROTOCOL 的跨 interface 状态别名。这样排除了“必须先发 GET_REPORT 才发生零包”的机制，且不依赖只读取一个 endpoint。
- USB power `runtime_status=active`、`control=on`、`runtime_suspended_time=0`；未发现浏览器进程。没有证据把这些零包归咎于 autosuspend 或网页独占。
- 上述 paired test 的 Boot Keyboard `SET_REPORT(Output, ID 0, length 1, data 00)` 在 Interface 1 ACK 成功；Interface 0 Report 的同类 LED output 也 ACK。发送的是保存过的 host LED 状态，没有改变 Caps 键逻辑状态。**只能证明请求完成，不能证明肉眼 LED 正确响应。**

USB reset 共两次，只针对 NUT75：

1. [从两个 Report 状态 reset](nut75-preboot-captures/standard-device-reset-check.log)，之后 GET_PROTOCOL 为 `(1,1)`。
2. [从已读回确认的两个 Boot 状态 reset](nut75-preboot-captures/reset-default-from-boot.log)，之后 **Interface 0=`0`，Interface 1=`1`**。

第二次 reset 后、GET_PROTOCOL 前的 usbmon 没有 SET_PROTOCOL 把 Interface 0 设回 Boot；它的状态随 reset 前状态保留，Interface 1 则恢复 Report。HID §7.2.6 要求初始化默认 Report，**这是 Interface 0 reset/protocol-state 恢复不正确的直接证据**。它声明 Boot Mouse，不应把 Boot Keyboard 专属的 F.3 条款错误套给它；依据是通用初始化要求。仍不能由此直接推出 Interface 1 Boot 输入格式错误。

抓包还确认 reset/rebind 时 Linux 对输入接口取 report descriptor、发 SET_IDLE(0)，但未发 SET_PROTOCOL。这是本机实际重绑定序列，不再只是参考 master 源码推测。reset 时 Linux 自动 SET_CONFIGURATION(1) 属于正常重新初始化，不是厂商命令/刷机。

最终状态：Interface 0/1 的恢复 SET_PROTOCOL(Report) 都 ACK，release 和 reattach 都成功；未为最后的独立 GET_PROTOCOL 再解绑一次。只验证恢复请求和驱动绑定，没有把节点存在说成实际按键已验收。

### 1.9 官方驱动源码与本机已保存配置：不能重复把 1000 Hz 当确定修复

[源码/缓存白名单摘要](nut75-preboot-captures/webdriver-settings-evidence.json)。只 HTTP 下载 JavaScript，没有执行其 USB/vendor 操作；只读厂商 origin 的 IndexedDB，仅抽取 VID/PID、版本和相关模式字段，没有复制账号、宏内容或完整配置。

官方 NUT75 配置明确 `isShowReportRate=true`、`reportRateList=[1000,4000,8000]`。UI 编码 `3=1000Hz`、`6=8000Hz`。本机缓存显示曾在 `6→3→6→3` 间切换，最后是 **1000 Hz**；缓存可过期，不代表现设备 live state。`nkroSwitch=0` 的设备语义未确认，不能当作 Boot/6KRO 已启用。

共享协议有 `nkroSwitch` 和“6键/全键无冲”“6键无冲”“全键无冲”功能定义，但功能列表按 model + firmware 返回的 defaultFnFuncIds 过滤。NUT75 的 model `fnFuncIds=[]`，旧缓存 Fn 映射没有这些动作；**不能因共享代码有字符串就建议强行写 vendor 命令或编造 Fn 快捷键**。

官方平台未认证的精确 NUT75 firmware metadata 请求返回“数据为空”；不能认定 1.40 最新或没有更新。没有下载/刷固件。

### 1.10 新现象对失效机制的约束：普通字母键产生鼠标动作

用户明确确认 BIOS / 引导时期、无 Fn 的 A 和 B 会让指针移动，并补充多个按键都是向下单次跳动。这是强行为证据：普通按键触发了预启动的鼠标动作，而且方向/触发方式与键盘 keycode 被当成 Mouse Y 位移高度吻合，不能再把故障概括为设备完全无响应。优先验证的是 Boot/interface 路由与主机报告解释不一致；仍未证明某个原始 keyboard report 被误解，也未定位具体 endpoint。

以下是**按标准格式推演，不是实抓包**：无 modifier 的 6KRO A=`00 00 04 00 00 00 00 00`、B=`00 00 05 00 00 00 00 00`。如果前三字节被按 Boot Mouse 的 buttons/X/Y 解码，就成为 buttons=0、X=0、Y=4/5。它能直接解释字母键导致位移，且与 Interface 0 的声明错位吻合。若设备发送合法 mouse report 或 HP 使用另一解析路径，也可能出现相似现象，所以移动方向、原始 packet 和绑定驱动仍有判别价值。

不要为了验证而在 BIOS 测 Ctrl/Shift 点击：在上述误解码机制下 modifier bits 可能成为鼠标按键，误改选项。普通字母键的移动方向观察比重复 Linux detach 更有信息增益。

### 1.11 2.4G 鼠标与有线 NUT75 的当前只读对照

后续只读 sysfs 核实：NUT75=`0c45:880c`，路径 `1-1`；可用鼠标接收器=`373b:11d9`，产品 `Wireless mouse 8k dongle-L`，路径 `1-2`。**两者都以 480 Mb/s 接在 usb1**，所以不能据此说 HP 不支持有线 USB 或 High Speed / 8k 类设备。无线链路在接收器内部完成，BIOS 面对的仍是 USB HID。

- 鼠标接收器 Interface 0：`03/01/02`，87-byte report descriptor 开头 `05 01 09 02 a1 01`（Mouse）。
- NUT75 Interface 0：`03/01/02`，62-byte report descriptor 开头 `05 01 09 06 a1 01`（Keyboard）。

这为接口声明/实际功能不一致的诊断提供直接对照，但仍不替代 Boot 状态原始包。当前连接快照只有有线 NUT75 和鼠标接收器，不能拿它证明 NUT75 自己的 2.4G 模式已通过或失败。用户表示尝试后仍不行；“2.4G 可以”指鼠标还是同一把键盘仍需区分，不能自动认定“同一把键盘无线可用”。

**修复边界**：没有取得或验证可安全刷入的 Boot-compatible 固件。修正 keyboard firmware 的 Boot interface/format/routing，或 HP UEFI HID handling，才是永久修复路径；修改 NixOS 或接口插入顺序不是补丁。特制 UEFI 输入驱动可以作为实验性的引导阶段绕过方向，但尚未实现/验证，不能保证修复原生 BIOS 设置界面。

## 2. 仍未确认的关键点

1. SET_PROTOCOL 成功且读回正确之后，实际 endpoint 输入是否随协议变化。
2. Boot 后 `82` 是否发送 8-byte 无 ID 6KRO；还是 NKRO、ID、鼠标数据、无数据。
3. 实际键盘 report 是否主要走 `81`，以及其声明 Boot Mouse 时的 Boot 数据；modifier 实际从哪个接口来。用户确认先前按键，仍缺少成功的正常 Report input 对照及设备 live 连接/配置状态。
4. GET/SET_IDLE 控制请求已成功，但 timed capture 没有 periodic report。Boot LED SET_REPORT 已 ACK，实际指示灯行为未验收。恢复驱动/协议成功，但实际按键恢复未验收。
5. HP 是否发了 `21 0b 0000 0001 0000`，是否发给错误 interface；请求之后输入长度及错误恢复。
6. ConInDev 候选是否真正聚合到 ConsoleInHandle；固件键盘驱动是否存在数据解析/事件通知错误。
7. cold/warm boot、不同插入时机、不同物理端口/USB-C/hub、另一台 UEFI 的结果。
8. Interface 0 在 USB reset 后保留 Boot 状态已实测；真正 power cycle 的默认值、初始化延时、真实 USB 电流、对应批次固件更新仍未确认。

**Linux usbmon 不能捕获发生在启动 Linux 以前的 HP UEFI USB 事务。** GET_PROTOCOL 在 Linux 中的值也不能回溯 HP 是否发送请求。

## 3. 可能原因排序

采用相对置信度，不给没有统计依据的精确百分比；候选不互斥。以下表格记录硬件采样时的排序。用户新增“BIOS/引导按键会移动指针”后，应首先验证 Boot 数据与鼠标解释是否错位；责任仍可能是键盘实现、HP 解析或两者交互，不把固件标准请求异常自动等同于唯一根因。

| 排名 | 原因 | 当前判断 / 证据 |
|---|---|---|
| 1 | NUT75 HID/Boot 固件及路由缺陷 | **首要嫌疑；标准请求和 Interface 0 reset 状态异常已有证据，BIOS 具体失效机制仍未证实**。GET_REPORT(Input) STALL；reset 不清 Interface 0 Boot；6KRO/NKRO 与 Boot 声明错位。ACK/读回正确不等于输入正确。 |
| 2 | HP/Insyde Boot HID 处理兼容性 | **中等嫌疑**。普通键盘正常，特定复合设备失败；可涉及 request/LED/idle/长度/聚合。ConInDev 含 interface 1，降低“完全没扫描 interface 1”的概率。 |
| 3 | 初始化时序、Fast Boot、端口/Hub 路径 | **中低嫌疑**。尚无 cold/warm、热插拔、hub 对照；当前 Linux 枚举正常不能排除预启动超时。 |
| 4 | HP 对 16-byte MPS 的实现限制 | **较低嫌疑**。MPS 合法，EDK II 参考实现支持；HP 独有硬编码未排除，属于第 2 项子原因。 |
| 5 | 供电 / 充电时序 | **低、待测**。100 mA 声明与手册 500 mA 值不一致，未见本次 Linux reset/disconnect 循环；需充满/关灯/供电 hub/电流对照。 |
| 6 | 独立 Limine bug | **极低首要嫌疑**。BIOS 已失败，当前版本只读 firmware ConsoleIn；mouse 禁用已无效。 |

UEFI 是否“按首个 TLC 当鼠标”“错误要求 MPS=8”“继续按 report descriptor 解码”均是可测试的实现假设，**没有已取得的 HP 源码或 issue 证明它们**。

## 4. 最有价值的下一步测试

### 4.1 首先测试 Interface 1 Boot 数据（最高信息增益；低至中风险；需要 sudo）

下列控制请求和输入采样已执行多轮，用户确认先前确实按键。不要继续盲目重复单接口解绑；下一步需取得真正成功的 Report positive control，或转为 preboot USB analyzer/EFI handle 取证。用内置键盘启动，先保存工作，关闭键盘网页驱动，勿在测试窗口输入密码。接口解绑期间 NUT75 部分或全部输入可能失效；其他接口仍绑定，可能出现重复普通输入。测试只动选定 NUT75 接口，不动内置键盘、鼠标、hub、整台 USB device。

只尝试 GET_PROTOCOL、无解绑：

```bash
cd /home/ran/nixos-config
sudo python3 assets/scripts/nut75-hid-probe.py --interface 1 \
  | tee /tmp/nut75-get-protocol.log
```

如果 `BUSY`：可能是 usbfs/usbhid interface ownership，不是键盘返回 STALL。需执行明确 opt-in 的完整测试：

```bash
sudo python3 assets/scripts/nut75-hid-probe.py \
  --interface 1 --exercise --ack-temporary-input-loss --seconds 8 \
  | tee /tmp/nut75-interface1.log
```

双接口复核脚本也已保存，默认无 ACK 参数时不访问 USB：

```bash
sudo modprobe usbmon
sudo python3 assets/scripts/nut75-paired-probe.py --ack-temporary-input-loss \
  | tee /tmp/nut75-paired.log
```

它同时轮询 `81/82`，输入窗口前不发 GET_REPORT，并验证目标产品、Boot 声明和 endpoint 大小。不能用没有成功 Report 对照的一轮零包判定 Boot 特有故障。

各窗口按提示依次按/松 A、Up、Enter、Shift+A。顺序：Report baseline → Boot（不改 idle）→ Boot idle=0 → Boot idle=125（500 ms）→ Report 恢复。每次打印完整 setup fields、返回/错误、actual_length 和 raw bytes。可选 `--led` 仅在能先读取原 LED output 状态时，短暂翻转 Caps bit 再恢复；默认不做 LED 写入。

严格请求表（Interface 1，均 endpoint 0）：

| 请求 | bmRequestType | bRequest | wValue | wIndex | wLength |
|---|---|---|---|---|---|
| GET_PROTOCOL | `a1` | `03` | `0000` | `0001` | 1 |
| SET_PROTOCOL Boot | `21` | `0b` | `0000` | `0001` | 0 |
| SET_PROTOCOL Report | `21` | `0b` | `0001` | `0001` | 0 |
| GET_IDLE | `a1` | `02` | report ID（Boot=0） | `0001` | 1 |
| SET_IDLE change only | `21` | `0a` | `0000` | `0001` | 0 |
| SET_IDLE 500 ms / all | `21` | `0a` | `7d00` | `0001` | 0 |
| GET_REPORT Boot input | `a1` | `01` | `0100` | `0001` | 8 |
| GET_REPORT Report ID 2 input | `a1` | `01` | `0102` | `0001` | 16 |
| GET_REPORT Boot LED | `a1` | `01` | `0200` | `0001` | 1 |
| SET_REPORT Boot LED | `21` | `09` | `0200` | `0001` | 1 + LED data |

这是 HID 1.11 §7.2 的 class/interface request，不是 vendor command。[1] Boot LED 是一字节数据、不带 ID prefix，即使 Report Protocol descriptor 没有 Output item，也不能据此否认 Boot 模式的 LED 要求。

判据：

- 按 A：Boot 应为 `00 00 04 00 00 00 00 00`；Shift+A 应 `02 00 04 00 00 00 00 00`。
- 按 Up：应包含 keycode `52`，不是 usage 对应的 bitmap。
- Report ID 2 的 A，按照该 descriptor，bitmap 起始为 `02 10 ...`，总长 16；这是 Report 正常形状，不是 Boot 正常形状。
- SET ACK + GET=0 不足以通过：必须看到实际按键后的 interrupt input 符合格式。
- `PIPE` 对控制请求通常意味着 STALL；`TIMEOUT` 可能是设备未响应；接收 interrupt 时 idle NAK 引发的 timeout **不是自动判错**。
- GET_PROTOCOL 需 exactly 1 byte，且只能 0/1；否则记录 malformed。
- Boot 稳定输出 16-byte bitmap、前缀 ID、错误 modifier、或状态切回 Report 后不恢复，分别是格式/状态实现 bug。
- 还需补测超过 6 个非修饰键时 ErrorRollOver、held-key idle rate 以及多次切换，才能扩大合规覆盖；最小工具不认证整台设备完全合规。

恢复措施：脚本 `finally` 尝试恢复 Report（Linux usbhid 需要 report 格式）、恢复读到的 idle rates、release、重新 attach 原驱动。已做语法、mock 正常/中断恢复及 privileged 硬件控制测试，本次两个接口 release / reattach 均成功；断线、SIGKILL、MCU 卡死时无法保证恢复。

若 NUT75 失去输入：用内置键盘停止测试，然后仅拔插 NUT75。若仅 reattach 失败，在确认当时仍是 `1-1:1.1` 后：

```bash
printf '%s' '1-1:1.1' | sudo tee /sys/bus/usb/drivers/usbhid/bind
```

不要 unbind hub/xHCI 或内置键盘；hidraw 编号和 USB 地址均会随重插变化。脚本每次按 VID/PID 和 sysfs 重新定位，只允许两个已知 Boot interfaces。

### 4.2 同样检查 Interface 0（高信息增益；同样需要 sudo）

```bash
sudo python3 assets/scripts/nut75-hid-probe.py \
  --interface 0 --exercise --ack-temporary-input-loss --seconds 8 \
  | tee /tmp/nut75-interface0.log
```

此时 wIndex=0、endpoint=81。它声明 **Boot Mouse**，因此不能用“Boot Keyboard 必须 8 bytes”去认证它；观察其 Report baseline 是否实际发送 6KRO，切 Boot 后是否按 Mouse 的固定前 3 bytes 格式转换，以及键盘 6KRO 数据是否一直被路由到这个接口。无 LED test。

若 Interface 1 Boot 错而 0 是真实 6KRO：向 WEIKAV 提交接口声明/路由缺陷即可有很强证据。若 1 Boot 完全正确：转向 HP request sequence、ConsoleIn 聚合、启动时序和复合接口兼容性。

### 4.3 usbmon 同步记录 Linux 请求（高信息增益；低风险；需要权限）

```bash
sudo modprobe usbmon
sudo timeout 75s tshark -i usbmon1 -w /tmp/nut75-linux-probe.pcapng
```

另一终端运行上述 probe；Wireshark display filter 如 `usb.bus_id == 1 && usb.device_address == 2`（先核对当前地址）。抓整个 bus 会包含其他键盘的输入，应限制保存范围、只按测试键、不输入秘密。`usbmon` 文本备用是 `/sys/kernel/debug/usb/usbmon/1u`；它同样会覆盖整个 bus。

若要看到 **Linux 驱动初次初始化**，先开始抓取，再用内置键盘只拔插 NUT75；仅加载 usbmon 不能回溯本次启动已经完成的绑定。地址将变化，应按本次枚举重新过滤。记录 GET_DESCRIPTOR、SET_IDLE、GET/SET_REPORT、SET_PROTOCOL（若出现）和返回状态；不要预设 Linux 一定发送 SET_PROTOCOL。

hidraw 可在 Report Protocol 下观察，但不能直接发送 SET_PROTOCOL，且 Boot 数据送进仍按 Report descriptor 解码的 usbhid 容易误读。故此测试使用 libusb interrupt transfer，而不是把 hidraw 权限当 BIOS 修复。

### 4.4 另一台 BIOS + 最小对照矩阵（高信息增益；无固件风险）

| 设备 | 同 OMEN / 同口 / cold boot | 另一台 UEFI |
|---|---|---|
| 普通 USB 6KRO | 已由用户报告成功；记录 VID/PID/descriptor | 验证测试平台正常 |
| 可切 6KRO/NKRO 的游戏键盘 | 分别记录两模式 | 记录两模式 |
| NUT75 | BIOS / Limine 分别记录 | BIOS setup 中测试 A/Up/Enter |

优先一台不同厂商：Dell、Lenovo、ASUS/MSI；记录 BIOS vendor（AMI/Insyde 等）和版本，不把 OEM 名称当独立 UEFI 实现。

其他 BIOS 正常 → HP 特定兼容性嫌疑上升，但其他 BIOS 可能容忍设备违规，不能代替 Boot 抓包。
多个不同 UEFI 都失败 → NUT75 Boot/descriptor 固件嫌疑大幅上升，仍不等同于所有 BIOS 都失败。

### 4.5 端口、hub、时序矩阵（中高信息增益；低风险；需要人工插拔重启）

依次：所有物理 USB-A → 简单 USB-C 转 A → **NUT75 → USB 2.0 hub → OMEN** → USB 3.x hub → 有外部供电的正规 hub。每种先只带 NUT75，不带 Compx mouse dongle/其他非必要复合 HID，检查接口冲突；不影响内置键盘。

每次记录：连接图、Linux `lsusb -t`、sysfs realpath、BIOS/启动前行为、冷启动和 warm reboot。现有两个 xHCI：`00:14.0 [8086:7a60]`、`23:00.0 [8086:1138]`（Thunderbolt 4 USB），但物理插口映射未实测；简单 USB-C adapter 和 Thunderbolt dock 不能混为一谈。

USB 2.0 High Speed hub **一般不能强制这把当前 480 Mb/s 的键盘变成 12 Mb/s，也不会改 descriptor/重排接口/转换 NKRO**；若要专门验证强制 Full Speed，需要明确只有 Full Speed 能力的 hub，不是仅包装写“USB 2.0”。High Speed hub 的 transaction translator 改变上游调度，hub 还可能改变 reset/power 时序，确实值得兼容性对照；它不是保证有效的协议修复。所谓“被动 USB 分线器”不是合规的数据 hub，不建议使用；区分 bus-powered 与 self-powered hub。

启动时机分别测：关机前已插、进入 BIOS 后再插、reboot、正常关机后冷开机。内置电池笔记本“拔掉充电器”不等于完全断电；不建议拆机/断电池，仅采用 HP 官方允许的完整关机方法。键盘有电池，USB 拔插也不一定 MCU power cycle；区分 USB reset 与真正 power cycle。

remote wakeup 是 suspend/wake 能力，不会使普通 BIOS 按键直接变成 keyboard input；100 mA 声明、真实充电负载需 USB 电流计或厂商确认。可以先充满电，按手册关灯/低功耗再对照，不把这些结果解释成 Boot 格式证明。

### 4.6 如果 Boot 数据正常：HP 阶段取证（最高定责价值；难度较高）

最直接方式是 USB 协议分析仪，从上电/复位到 BIOS setup 抓 EP0 和 `81/82`，核对 actual SET_PROTOCOL interface、返回/STALL、SET_IDLE、LED 初始化顺序、IN payload 和 reset 时序。

没有分析仪时，可用可信 EFI Shell 检查 handle / driver / device path / Simple Text Input / Input Ex / USB_IO；或者一个最小 EFI app 分别读取设备 input handle 与 ConsoleIn，分辨“设备 driver 无 key”与“没有 console 聚合”。UEFI app 读 GET_PROTOCOL 只能反映当时状态，不能证明之前是谁发送 SET_PROTOCOL。先只读；不把加载第三方 DXE 驱动作为无风险操作，也不要写 ConIn/ConInDev 做盲目修复。

## 5. 可实施修复

- **最可靠低风险 workaround**：内置键盘/已知正常的 USB 6KRO 用于 BIOS/Limine；NUT75 进入 Linux 后使用。可选择默认启动项/超时减少菜单操作，不能恢复 BIOS 按键。
- **配置/模式恢复而非已验证 BIOS 修复**：确认 `Fn+T` 有线；官方 UI 若显示 8000/4000 Hz 可改 1000 Hz，但本机最后缓存已为 1000，不能当新发现的必有效方案。按手册 `Fn+D` 回常规延时也不是 6KRO/BIOS 开关。只有 device-filtered 官方界面实际提供 6KRO 功能才考虑；不要强行使用共享代码中的隐藏值。
- **可选恢复出厂**：先通过官方界面备份键位、宏和灯效，再按手册 `Fn+Esc` 长按 3 秒恢复。这可能清理锁键/配置/测试状态，但会清除自定义设置，未执行且不保证 BIOS 修复；不能修复编译进固件的错误 interface 声明。不要尝试未说明的生产测试/Fn 组合键。
- **BIOS 设置**：若该 SKU 实际提供 Fast Boot/USB selective initialization，先关 Fast Boot；若存在 USB Keyboard/Legacy USB/preboot USB 支持，启用。记录原值，一项一项测试。未确认 OMEN F.28 一定提供这些选项。xHCI handoff 主要关联 firmware→OS 交接，通常不是 BIOS setup 无输入的直接修复；勿盲目开 CSM/改 boot mode。Secure Boot 本机已关闭，无需继续切换。
- **port/hub**：USB 2.0 hub、另一 root port、简单 USB-C adapter 的成功组合可以保留作为 workaround；只有实测成功才称有效。
- **HP BIOS update**：先获取对应 SKU/board release notes；有 HID/preboot/composite 修复或 HP 技术支持确认后，按官方流程考虑。升级 BIOS 不属于无风险；准备 Windows BitLocker recovery key（若启用）、接稳电源、确认机型和回退限制。未取得 changelog，不能承诺升级有效。
- **最有证据基础的根本修复路径：WEIKAV corrected firmware / replacement**。先确认 MCU/PCB/批次和精确官方 updater；提交 GET_REPORT STALL 与 Interface 0 reset 状态保留日志。请求把真实专用 6KRO 接口明确声明 Boot Keyboard，提供对应 8-byte Boot input / LED，其他复用/vendor 功能独立 non-boot（或正确实现对应 Boot Mouse），修复 GET_REPORT、idle、USB reset 默认状态。若厂商不提供适配这批 NUT75 的 Boot-compatible 修复、且预启动输入是刚需，则更换为已实际通过 BIOS 的型号；不能声称现在已有可安全刷入的修复包。
- **bootloader**：现版 Limine 无 direct HID fallback；换同样只使用 EFI ConsoleIn 的 bootloader 不应期待自动解决。带 native USB keyboard driver 的其他方案或定制 EFI driver 理论上能绕过部分 firmware 问题，但需实际构建/模式支持，不能说“换 GRUB 必定修复”。不建议在排障初期为此改主启动链。
- 不刷第三方 QMK，不使用其他 WEIKAV 型号 firmware，不走 ISP/SWD。即使理论上 MCU 可重刷，仍涉及未知 bootloader、matrix、供电/无线/RGB、电池管理与变砖风险，不是当前方案。

## 6. 不值得继续尝试的方向

已不构成 BIOS 阶段解决方案：NixOS udev / hidraw ACL / Chromium WebHID、Linux kernel parameters / xHCI Linux quirks、调整 Linux hid polling、继续反复设置 Limine `mouse: no`。

这些 Linux 机制可用于 **获得测量权限或观察 Report 数据**，不能修复先于 Linux 的 UEFI driver。也不值得仅因 endpoint=16 就判违规、仅因 NKRO 就判 Boot 失败、仅因 Boot subclass 声明就判合规、仅因 VID 名称 Microdia 就套用别的设备固件。
